We devide our testing efforts into several areas.

1. General
When we test different areas, create test cases in .typ form and name them accordingly. Put them into the appropriate folder (or create new ones if you don't find anything fitting)

We want to create tests that should succeed (default) and also tests,
that are expected to fail. We will say so in the latter case. Code
adaptations may be necessary, since we often use assertions instead
of real user errors or warnings.

4. Forsyth-Edward-Notation (FEN)
Note: unlike PGN, that is almost always created by software-based exporters and therefore should be valid, the same isn't necessarily true for FEN. There are numerous things that can go wrong.

First (no error): if a FEN string doesn't contain spaces, it means it misses meta data. Just add silently " w KQkq - 0 1" in such a case.

4.1 Wrong number of sections
FEN string must contain 8 sections separated by "/", create test for success and failure. For failure, create meaningful user facing error message.

4.2 Wrong characters used
Characters must come from set "bpknqrBPKNQR". 
Create pass and fail test, create user facing error message in latter case.

4.3 Inconsistencies
- number kings of same color exceeds 1
- number of pieces and free squares in onw "/" section doesn't add up to 8 (but other conditions are correct).

4.4 Metadata problems
- side to move must be present, can only be "w" and "b"
- castles permissions must be there, can either be "-" or combinationss "K", "Q", "k", "q".
- en passant target is either "-" or an square. In case of real square, there should be an appropriate pawn (for example: black to move, en passant is e3, white should have moved e2-e4 so there's a pawn on e4).
- half move and full move clock must be there.
