1. Task: you are tasked with developing a Typst plugin for displaying
	chess diagrams. We want this for publications of chess games and chess
	tournaments in PDF using Typst. 
	
	At the mandatory minimum this would involve
	- displaying a chess board and pieces on it
	- reading in a string in "Forsythe-Edwards-Notation" ("FEN") and 
		creating a chess diagram.
		
	Further optional enhancements would involve:
	- reading in games (one or several at once) using game notations in
		"Portable Game Notation" format ("PGN")
	- displaying chess diagrams at arbitrary points in the game true (e.g.
		after move 30 from white).
	- possible internationalization of chess terms (if used)
	- further customizations of the displaying capabilities.
	
	In the following, we don't want to develop code yet, we rather discuss
	different options for coding the subtasks explained below. No code yet,
	until I say so!
	

2. Subtasks:
	2.1 Board and Piece Display
	We must be able to display a chess board (8x8 squares of alternating dark and
	light background) and we must be able to put arbitary chess pieces on arbitrary
	squares of the board.
	
	There are different ways to do that in Typst: we could use a table of grid
	based layout or draw freely using the drawing functions of Typst (see
	https://typst.app/docs/reference/visualize/). We also could used tiling of
	rectangle. Discuss the best approach for a board.

	size: size of chess diagram should be freely adjustable, but
	as a default it should fit into a two column layout of either
	"us-letter" or "a4" (whatever is smaller in width). If size
	is smaller than "0" we jump to default size. If size is larger
	than available width and / or height, we adjust the size to
	the largest width / height that still fits on a page.

	We also must be able to add support labels for rank and files. Files must
	be named "a" to "h" and ranks must be labeled "1" to "8". The default would
	be labeled chess boards (can be switched off) and the default would be
	file labeling below the board and rank labeling on the right side. But
	rank label can also be left and file labeling also on top of board if we
	chose to do so.
	
	For now, we chose a fixed color for dark and light sqaures. 
	
	We must able to put pieces of arbitray kind and color on arbitrary squares
	using "A1" / "a1" (capitalization doesn't matter). For now, we use a fixed
	set of pieces from Unicode.
	
	
	All this necessitats, we have mapping for squares from file 1 / rank 1 => "A1"
	in the lower left corner to file 8 / rank 8 => "H8" in the upper right corner.
	
	When putting a piece on a square, we must be able to designate piece kind
	(king, queen, rook, bishop, knight and pawn) and piece color ("white" or "black")
	and then put it on a square as outlined above. At this stage, we don't care, whether
	we have a valid chess position, we just draw:
	
		draw_piece(piece_kind, color, square).
		
	We also want to wrap the chess diagram in a #figure() element for adding
	captions and labels. This way we can later develop an "outline" tailore to
	chess diagrams.
		
	The chess figure also shall include the possibility to use name of opponents
	and year at the minimum. 
	
	
	2.2 Forsyth-Edwards-Notation
	Creating chess diagrams / figures this way would be very tedious, much better
	is the use of specialized chess notations like the "Forsyth-Edwards-Notation" ("FEH"),
	see also for example .
	
	With that we can parse strings like the following:
	
		rnbqkbnr/pp1ppppp/8/2p5/4P3/5N2/PPPP1PPP/RNBQKB1R b KQkq - 1 2
	
	which arises after moves 1.e4 c5 2.Nf3 and create a diagram from it.
	
	In order to extend Forsyth-Edwards-Notation / FEN properly we must also extend
	also our notion of a position. Rather than the simple square mapping in subtask 3.1,
	we have a sophisticated "position" element, that keeps track of all pieces on all
	squares, the full moves played, the half moves since last capture or pawn advance,
	which player has the right to play and the remaining castling options.
	
	We would give a FEN string plus the additional options about players and years and
	we get a fully fledged chess diagram already.
	
	
	2.3 Portable Game Notation
	We must support complete games using "portable game notation" (= "PGN"), see e.g.
	https://en.wikipedia.org/wiki/Portable_Game_Notation. As an example for studying
	the structure, I added two PGNs in folder "examples/pgn" in this project. 
	
	They both describe the well-known game 5 from the Spassky-Fischer world championship in 
	Reykjavik, Island in 1972. As you can see, they have additional tag pairs beyond
	the mandatory "Seven Tag Roster". 
	
	To understand the actual move / move text, this also necessitates the development of a 
	fully fledged "move generator" just as chess engines do in order to read in moves and
	check for validity of them and advance the internal state of a position. In a PGN, moves
	are given in "Standard Algebraic Notation" ("SAN", see for example
	https://en.wikipedia.org/wiki/Algebraic_notation_(chess)). Note that SAN differs from
	algbraic notation in couple of subtleties (especially pawn promotion). 
	
	Parsing would involve:
	- translating an ambigous move like "1.e4" into an unambigious move like "1.e2e4"
		(= "pawn e2 moves to e4 in first move") and
	- compares that to the internal list of
		valid moves it has generated for the position (here: the starting position). If
		the translated PGN / SAN move appears in that internal list, the move is valid and
		we advance to the next move. We expect PGNs to be valid, but if we encounter an
		invalid move, we must "panick".
	
	PGN also allows for the use of "Numerical Annotation Glyphs" ("NAG"). We want to support
	the standard 140 NAGs, using symbols instead of text is preferred. NAGs start with '$'
	appended by a number from '0' to '140', e.g. '$1' which means "good move". We would
	use a '!' instead in the text. When reading in a PGN, our code must find a meaningful
	translation to text.
	
	Our parser must also support comments (non nesting) which start with '{' and end with
	'}'. Also supported must be variations (possibly nesting), which start with '(' and
	end with ')'.
	
	Input: we must both support reading in external PGN files (like the two examples given
	above) via a function #pgn-file(<PGN_FILE>) and reading in games from within the main 
	".typ" file. I would suggest a function like #pgn(<TEXT IN RAW FORMAT>).
	
	Diagrams from PGNs: we must be able to insert a digram from a PGN after a designated
	move (and possibly color). This may pose the problem how to designate diagrams for
	variations. I strongly dislike the idea of altering existing, exteranal PGNs. Please
	suggest a suitable solution here. For PGNs in in main text via raw text input, it
	might be possible to have a special comment like with content "#chess-diagram-here()"
	or something appropriate.
	
	Note also, that a PGN can contain several games. This might be important later.
	For now, we assume, a PGN contains one game, though.
	

	2.4 Improve Drawing
	We have to improve drawing a bit:

	Diagram / Figure labeling: 
	For labeling the diagram itself, I propose the following rules:
	- if players and year are known, we want a label _above_ the diagram with
		"<PLAYER_WHITE> - <PLAYER_WHITE> (<YEAR>)" is automatically drawn, other
			wise there's no label above.
	- a manual "label_above" / "game_info" overrides the default and will be drawn above the diagram.
	- For diagrams originating from FENs, a default caption "Position at move <FULL_MOVE>, <COLOR> to play"
		is drawn below the diagram.
	- For diagrams originating from PGNs, a default caption "Position after move <LAST_MOVE_IN_PGN>"
		is drawn below the diagram.
	- a manual "caption" overrides the default and will be drawn below the diagram.
	- for diagrams originating from a piece / position dictionary, there will be no default labeling.

	Different sets of chess pieces:
	The biggest change in drawing, that also affects existing code: we want to support
	different sets of chess pieces as SVGs for drawing, which using the unicode characters only
	as fallback. In folder "assets/piece_sets", we see six different sets of chess pieces with
	"cburnett" as the default. The drawn SVGs already have the correct baseline, so remove any
	baseline adjusting code (exception: fallback / unicode drawing option).
	The used chess piece set must be an adjustable option, which "cburnett" as the factory default,
	then either "#set-piece-set(<PIECE_SET)" or as part of a drawing style. But users must be
	able to change piece sets for individual diagrams.

	Adjustable colors:
	Colors must be adjustable and settable as default option. For a start, use what you are currently
	using as default options. If users change the default, the new default must be used for
	subsequent diagrams, until option is reset or changed to another default.

	Board labeling:
	Board labeling should use it's own sans-serif font (Helvetica, Arial etc.) independet what
	is set otherwise for the main text or diagram labeling. This should be not adjustable
	for now. We want to support three modes
	- on square (the default): we want small labels "a"-"h" for the files and "1-8" for the rank
		_on the squares_! The file labels ("a"-"h") would be on the first rank (bottom left corner of
		squares a1 - h1) and the rank lables on the last file (h1-h8) at top right corner.
		This rank labels would be on the last file ("h") as "1" to "8" on squares "h1" to "h8". This also means that square "h1" has two(!) labels
		"a" at bottom left and "1" on top right corner of the square.
		The colors of the labels must be that of the opposite color of the respective squre.
	- the second style for board labeling is the same as before.
	- the third style would involve drawing a border of some points width around the actual
		board in the darker field color and label the board with the light field color.
	- The option to not label the board must still be respected!
	- The option to move file labels to top and rank labels to left must still be respected,
		but the position of those labels are still "file label: bottom left" and "rank label: 
		top right" on the respective field for first (default) option.
	
	Board flipping:
	Boards are by default oriented as white / bottom and black / top. There must be an option
	flip this orientation to white / top and black / bottom. Piece positioning must be
	adjusted accordingly. Labeling the board must be adjusted accordingly!
	Flipping is _not_ an option you can set as style default, it must be turned 
	on specifically for each affected diagram.



	2.5 Internationalization
	In the future, we want to extend the Typst plugin for support of arbirary languages
	for chess diagrams and annotations. After setting the languge with '#set text(lang: "LANG_ABBREV")'
	we would switch to that language for chess diagrams.
	
	
	2.6 Additional Customiaztions
	Ideas for further customizations:

	- support for match / tournament tables (like a cross-table), by reading in either JSON
		files or PGNs (one PGN can contain several games).
