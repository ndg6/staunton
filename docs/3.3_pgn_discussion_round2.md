## What changed vs. round 1

Two upgrades, everything else stands:

1. **Lazy two-phase parsing** (from the tournament insight): parse headers +
   movetext tree eagerly and cheaply; defer engine resolution (resolved moves +
   positions) until a diagram actually asks. A crosstable that only reads results
   never runs the engine.
2. **Style refactor of the existing renderer**: introducing `diagram-style` means
   collapsing the renderer's ~13 display kwargs into one merged `style` dict and
   adding `orientation` / `piece-set` / `highlights`. Modest, localized, worth
   doing before 3.3 grows.

## 1. Move generator — two-stage split (confirmed)

Standard "copy-make + king-safety" approach, and easier to get right than
fully-legal generation with explicit pin/ray tracking.

- **Stage 1 — pseudo-legal generator**: every move respecting piece geometry,
  blockers, captures, castling-squares-empty, and the en-passant target — but
  ignoring whether the mover's own king is left in check. Purely mechanical.
- **Stage 2 — legality filter**: for each pseudo-legal move, `apply` it to a copy
  of the position, then ask *"is the moving side's king attacked now?"*. If yes,
  discard.

Keystone primitive: **`is-square-attacked(position, square, by-color)`**. Used
for king-safety (stage 2), check/`+` detection, **castling legality** (king not
in check, doesn't pass through or land on an attacked square), and eventually
mate/stalemate (`legal-moves` empty + king attacked ⇒ mate). Write and test it
hard; everything leans on it.

**Performance**: a single game is ~80–150 plies, ~30 pseudo-legal moves each, one
generation per ply — trivial in Typst.

**Tournament insight (adopted as a design rule): two-phase, lazy on the
expensive half.**
- **Phase A (cheap, eager, all games)**: tokenize headers + build the movetext
  tree with `san` strings only. Pure string work, no engine.
- **Phase B (expensive, lazy, per-game)**: run the engine to fill each node's
  `resolved` move + resulting position. Triggered only when a diagram asks for a
  position.

A crosstable reading `game.tags.Result` for 500 games never enters Phase B. This
supersedes the earlier "precompute mainline positions" note: still precompute,
but only on first navigation of *that* game.

Language: **pure Typst**, confirmed.

## 2. Structures

### 2.2 What "flags" means (explanation requested)

`flags` is the **special-move metadata** on a *resolved* move — what `from`/`to`
alone can't express but that both `apply()` and the renderer need:

| flag / field | why it must be recorded |
|---|---|
| `capture` (+ which piece) | board removal; halfmove-clock reset; `last-move` display |
| `double-pawn-push` | this move *sets* the en-passant target for the next ply |
| `en-passant` | captured pawn is **not** on the destination square — `apply` removes a different square |
| `castle-king` / `castle-queen` | the **rook** moves too; renderer may highlight both |
| `promotion` (+ target piece) | the pawn is *replaced* by Q/R/B/N on arrival |
| `check` / `checkmate` | drives the `+`/`#` glyph; derivable, but cheap to store once computed |

Suggested model:
`(kind: "normal" | "capture" | "double-push" | "en-passant" | "castle-k" | "castle-q" | "promotion", captured: none|kind, promotion: none|kind, check: bool)`.

Storing flags (rather than re-deriving) makes `apply` a clean switch on `kind`
(no re-scanning to guess "was this en passant?"), and hands the renderer
special-move info for free.

### 2.3 diagram-style — two questions answered

**Q: still set an individual style for a single diagram?** — **Yes.** Resolution
is a three-level merge: **explicit per-call arguments → current document default
→ built-in defaults**. Per-call always wins.

The "set defaults for everything after this point" behaviour mirrors Typst's own
`#set` via document-order **state**: a `state("staunton-style", builtin)`, a
setter `set-chess-defaults(...)` that updates it, and each diagram reads the
current state via `context` and merges. Gives "default, then change for
subsequent diagrams" while keeping per-call overrides.

**Q: repercussions for existing render functions — must we adapt them?** —
**Yes, a modest, localized refactor.** Today `render-board` takes ~13 individual
display kwargs (`light`, `dark`, `labels`, `file-side`, `rank-side`, fills,
fonts, scales…). With `diagram-style`:
- collapse those kwargs into **one resolved `style` dict** the renderer reads
  from (the inner `place` loops barely change — they read `style.dark` instead of
  a `dark` parameter);
- add a **merge step** (built-in ⊕ state ⊕ per-call);
- add the **new style fields** 3.3 needs — `orientation`, `piece-set`,
  `highlights` — so the coordinate→offset function gains one `orientation` branch
  (flip when Black is at the bottom) and the piece layer reads `piece-set`
  instead of hardcoding Unicode.

Keep the convenient top-level kwargs on `chess-diagram` as **sugar** that builds a
one-off style, so nothing already written breaks for callers.

### 2.4 Locators for nested variations — worked example

A `path` locator names a sequence of **"advance to a move, then descend into one
of its variations"** hops, ending with a final advance in the deepest line.

PGN with two-deep nesting:

```
1. e4 e5 2. Nf3 (2. Bc4 Bc5 (2... Nf6 3. Ng5)) 2... Nc6 3. Bb5
```

Tree:
- **Mainline**: `e4 e5 Nf3 Nc6 Bb5` (Ruy López).
- Branching at White's 2nd move, **variation 0** = Italian: `2. Bc4 Bc5`.
- Inside that line, branching at Black's 2nd move, **variation 0** = Two Knights:
  `2... Nf6 3. Ng5`.

Locators:

```
// Mainline, position after 3.Bb5 — no descent:
(line: (), at: "3w")

// Italian line, position after 2...Bc5 — descend once:
(line: ( (at: "2w", into: 0), ),                       at: "2b")

// Two Knights, position after 3.Ng5 — descend twice:
(line: ( (at: "2w", into: 0), (at: "2b", into: 0) ),   at: "3w")
```

Read the last as: *start on the mainline → go to White's move 2 → step into
variation 0 (Italian) → go to Black's move 2 → step into variation 0 (Two
Knights) → take the position after White's move 3 (Ng5).* Each `into:` index
disambiguates when a move has several alternative variations. Mainline diagrams
use `line: ()`, so the common case stays terse (`"30b"`).

## 3. Functions reading PGN — confirmations & the `raw` decision

- **Hard errors on malformed PGN** — locked in (offending token/move + position
  in the message).
- **Lenient Seven Tag Roster** — missing tags default; unknown tags preserved in
  the open `tags` dict.
- **Inline = `raw` only, supporting both `#raw(...)` and the ` ``` ` block** —
  both forms produce the same Typst **`raw` element**; we read its `.text` field.
  Why raw is the *right* requirement (not just convenient): PGN tag pairs are full
  of double-quotes (`[White "Spassky, B"]`) and movetext spans many lines — a
  normal string literal forces escaping and `\n`, whereas a raw block preserves
  text **verbatim**.
  - **file path** → Typst's `read(path)` → string → `parse-pgn`;
  - **inline** → a `raw` element (from `#raw(..)` or a fenced block, optionally
    tagged ` ```pgn `) → take `.text` → `parse-pgn`.

  `parse-pgn` normalizes its input: if it's a `raw` element take `.text`, if it's
  already a string use it directly. One normalization covers all three entry
  points (file, `#raw`, fenced block) with no duplicate parsing logic.
