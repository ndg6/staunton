# Subtask 3.3 — PGN support: design discussion

> Status: **discussion only, no code yet.** Captures the options weighed for PGN
> import, the move generator, the data structures, and how diagrams are produced
> for the mainline and for variations. Subtasks 3.1 (board/piece display) and
> 3.2 (FEN) are already implemented.

## Decisions still open

1. **Engine**: commit to a pure-Typst move generator for v1, or invest in a
   WASM engine up front because large PGN databases are expected?
2. **Author-variation ergonomics**: is a `line(from, moves)` overlay enough, or
   do we want a richer notation for building our own annotated variation trees
   in Typst?
3. **SAN scope for v1**: all of standard SAN (recommended); Chess960 castling
   deferred?
4. **Robustness**: hard-error on unresolvable/illegal SAN (recommended) vs.
   best-effort rendering?
5. **Multi-game return**: always return an array of games (recommended) vs. a
   bare game for the single-game case?

---

## The crux: PGN inescapably needs a move generator

Everything in 3.3 hinges on one thing that 3.1/3.2 didn't need: to turn movetext
like `Nf3` into a diagram, you must know *which* knight goes to f3 and *what the
board looks like afterwards*. That requires generating the legal moves of a
position. This is the single most important decision in 3.3.

Why SAN forces real legality (not just pseudo-legal moves):

- **Disambiguation depends on pins.** If two knights could go to d2 but one is
  pinned to the king, SAN writes `Nd2` (no disambiguation) because only one move
  is *legal*. To resolve that correctly you must detect that the pinned knight
  can't move — i.e. full legality, including "does this leave my king in check."
- SAN also encodes castling (`O-O`), en passant, promotion (`e8=Q`), check (`+`),
  mate (`#`) — each needs board state and rules to apply and to update castling
  rights / en-passant square / clocks.

So 3.3 = a parser **plus** a rules engine. Two ways to get the engine:

**Option A — pure Typst engine.**
- *Pro:* self-contained, zero build pipeline, works identically in the web app
  and on Universe, hackable, easy to unit-test in-language. Games are bounded
  (rarely >150 plies), and a document has a finite number of them, so raw speed
  is tolerable.
- *Con:* legality checking (attack maps, pin/check detection) is real work to
  write and verify; Typst is not fast, so a document replaying dozens of long
  games *could* feel sluggish at compile time. Mitigable with memoization.

**Option B — WASM plugin (compile a Rust engine such as `shakmaty`).**
- *Pro:* correct and fast SAN parsing + legality out of the box; trivial replay
  of huge PGN databases.
- *Con:* a real build/release pipeline, the bytes-in/bytes-out serialization
  boundary to design, and more to maintain. WASM *does* run on the Typst web
  app, so portability isn't the blocker — maintenance is.

**Recommendation (unchanged from the 3.2 discussion):** start with a
**pure-Typst engine behind a narrow interface** — essentially one function
`legal-moves(position) -> array<move>` plus `apply(position, move) -> position`.
Build SAN resolution and PGN replay strictly on top of that interface. Then if
compile-time performance becomes a problem on big inputs, the engine is the
*only* thing that swaps out for WASM, and the parser/diagram layers don't change.
This keeps the seam we already established (position model → renderer) and adds
one more clean seam (engine → SAN/PGN).

## Structures needed

Four structures, in two groups — and the PGN-vs-diagram separation you asked for
falls out naturally.

### Group 1 — game data (the "what", read-only after parsing)

1. **`game`** — one parsed PGN game:
   - `tags`: dict of all header tags (the Seven Tag Roster — Event, Site, Date,
     Round, White, Black, Result — plus extras like `FEN`, `SetUp`, `ECO`,
     `WhiteElo`). Keep it an open dict so unknown tags survive.
   - `start`: the initial position (standard, *or* seeded from a `FEN`/`SetUp`
     tag — must handle this).
   - `tree`: the movetext as a **tree**, not a list (see below).
   - `result`: `1-0` / `0-1` / `1/2-1/2` / `*`.

2. **`move` (a tree node)** — PGN movetext is recursive (variations nest), so a
   node holds:
   - `san`: the move as written (`"Nf3"`, `"exd5"`, `"O-O-O"`, `"e8=Q+"`).
   - `resolved`: the concrete move once the engine interprets it —
     `(from, to, piece, capture, promotion, flags)`. Storing both means SAN is
     parsed once and never re-resolved.
   - `number` / `side`: fullmove number and white/black, for locators and display.
   - `nags`: numeric annotation glyphs (`$1` = `!`, `$2` = `?`, …) and/or inline
     `!?`.
   - `comment-before` / `comment-after`: the `{…}` text.
   - `variations`: an array of alternative sub-lines branching *before* this move
     (each is itself a list/tree of `move` nodes). **This is the RAV (Recursive
     Annotation Variations) tree** — the reason `tree` is not a flat array.

   The **mainline** (the "principal variation" — the game as played) is just the
   spine: follow the first child at every node, ignoring `variations`. A
   `mainline(game)` accessor gives the flat ply list; the full `tree` preserves
   branches.

   *Design choice to settle:* store the resulting **position at each node** too,
   or recompute by replay? Recommendation: **precompute and cache positions along
   the mainline** once per game (so any number of mainline diagrams are O(1)
   navigation), and compute variation positions lazily on demand. This is the
   main performance lever for a pure-Typst engine.

### Group 2 — presentation (the "how it looks", decoupled)

3. **`diagram-style`** — the specialized display info, kept entirely out of the
   game data: `size`, `light`/`dark` colors (or a named theme), `piece-set`
   (Unicode now, image sets later from 3.5), `labels` + sides, `orientation`
   (white/black at bottom — needed for diagrams from Black's view), plus optional
   **highlights** (`last-move`, arbitrary marked squares) and later **arrows**. A
   diagram from a game would default `last-move` highlighting to the move that
   produced the position — a natural feature once moves are resolved.

4. **`locator`** — a tiny value that points *into* a game at a specific point, so
   a diagram can say "the position here." Candidates:
   - by move number + side: `"30w"` / `"30b"` (human-friendly, matches "after
     move 30 from white");
   - by ply index: `42`;
   - by a **path** for variations: e.g. `(ply: 18, variation: 0, then: 3)` —
     descend into the tree.
   Recommendation: support `"30w"`-style strings for the common case and a path
   form for variations.

**Why this split is the right call:** a diagram is produced by **`position` +
`diagram-style`**. The position comes from *either* a FEN (3.2) *or* navigating a
`game` (3.3). So the renderer never knows whether its position came from a string
or a game — and `diagram-style` (piece sets, colors) lives only on the
presentation side, never polluting the PGN record. That is precisely the
encompassing-vs-specialized division requested.

## Functions for reading PGN

Layered, so the file-vs-inline distinction is trivial:

- **`parse-pgn(string) -> array<game>`** — the core. One PGN file can hold *many*
  games (tag block, movetext, blank line, repeat), so the return type is an array
  even for one game. Internally:
  - a **tokenizer**: tag pairs `[Key "Value"]`, move numbers (`12.`, `12...`),
    SAN tokens, NAGs (`$N`), comments (`{…}` and `;`-to-end-of-line), variation
    parens `(` `)`, result token, null moves (`--`/`Z0`).
  - a **movetext parser** producing the tree, recursing on `(` … `)`.
  - **SAN resolution** via the engine to fill each node's `resolved` + position.

- **External files: `read-pgn(path)`** — thin wrapper that uses Typst's built-in
  `read(path)` to pull the file as a string, then `parse-pgn`. Decision to flag:
  **encoding** — `read` gives UTF-8; old PGNs are often Latin-1, so we either
  document "save as UTF-8" or add a decode step.

- **Inline PGN in a `.typ` file** — no new parser needed; it's just a string. Two
  ergonomic entry points:
  - pass a normal (multi-line) string literal to `parse-pgn`;
  - accept a `raw` block / the content of a fenced block so authors can paste PGN
    verbatim without escaping. Recommendation: support a string argument as the
    baseline and consider a `raw`-friendly variant for nice authoring.

- **Selecting among multiple games**: `parse-pgn(...).at(i)`, plus maybe a
  `find-game(games, white: .., event: ..)` helper. Decide whether the common
  single-game path returns the game directly or always an array (lean: always
  array, with a documented `.first()`).

Robustness decisions to settle now (same spirit as the FEN choices):
strict-with-clear-errors on malformed movetext vs. best-effort; whether an
illegal/unresolvable SAN is a hard error (recommend yes, with the offending move
+ position in the message — silent wrong diagrams are worse in publishing); how
much of the Seven Tag Roster is mandatory (PGN spec says all seven, real-world
files omit them — be lenient).

## Producing diagrams: principal variation vs. variations

This is where the read-only game + overlay design pays off.

**Principal variation (the game as played).** Just navigation of the mainline
spine:
- `position-after(game, locator)` → position at that point.
- Convenience `board-after(game, "30w", style: …)` → a finished diagram
  (position + style → renderer + figure).
- A "filmstrip" helper that emits diagrams at a list of locators, or every N
  moves, is a natural add.
- Because mainline positions are precomputed, generating many such diagrams is
  cheap.

**Variations — two distinct kinds, both without touching external PGNs:**

1. **Variations already inside the PGN (RAVs).** They're parsed into the
   `variations` of the tree, so they're addressed by a **path locator** and
   rendered exactly like the mainline. Nothing is mutated — you're just
   navigating a different branch of the already-parsed, immutable tree.

2. **User-authored "what-if" variations in the `.typ` file.** This is the key to
   "without altering external PGNs": the parsed `game` stays read-only;
   exploration happens in an **overlay** computed in Typst.
   - `line(from: <locator | position>, moves: (...))` — start from a node (or a
     bare position/FEN) and apply a sequence of moves (SAN or coordinate pairs)
     through the engine, returning a fresh list of positions. The source game is
     never modified; you have just produced new derived positions.
   - Then `board-after(thatline, k, style: …)` diagrams any point of the
     hypothetical line.
   - Because `line` only *reads* the starting position and runs the pure engine,
     it is naturally non-destructive — Typst values are immutable anyway, but the
     design makes the intent explicit: external PGN in, derived positions out,
     original untouched.

So: **mainline = navigate the spine; PGN variations = navigate a branch; author
variations = `line(...)` overlay**. All three feed the same `position +
diagram-style → diagram` path.

## Cross-cutting decisions to settle before coding

- **SAN coverage checklist**: castling (`O-O`/`0-0`), captures (`exd5`), en
  passant, promotion (`=Q`, and `e8=Q+`), disambiguation (`Nbd2`, `R1e2`),
  check/mate (`+`/`#`), null moves. Decide what's in scope for v1 (recommend all
  of standard SAN; skip Chess960 castling notation initially and note it).
- **Engine scope**: full legality (needed for SAN as argued) — but consider a
  fast path that *trusts* explicit disambiguation in the PGN and only invokes
  pin/check analysis when the move is otherwise ambiguous. Big speed win on a
  pure-Typst engine.
- **Performance**: parse-once / precompute-mainline-positions / memoize; document
  that a `game` should be bound to a `#let` and reused, not re-parsed per diagram.
- **`FEN`/`SetUp` tag**: games not starting from the standard position must seed
  `start` from the tag — easy to forget, breaks everything downstream if missed.
- **Orientation**: diagrams from Black's perspective need board flipping in the
  renderer — a `diagram-style` concern, but the renderer's coordinate function
  must support it (we built it in a way that makes this a localized change).
- **Terminology note**: "principal variation" classically means an engine's best
  line; here it means the game's mainline. Recommend naming the API
  `mainline`/`board-after` to avoid confusion for chess-literate users.

---

## Summary recommendation

Pure-Typst engine behind a narrow `legal-moves`/`apply` interface (WASM later
only if needed); four structures — `game` + `move`-tree (encompassing,
read-only) and `diagram-style` + `locator` (presentation); `parse-pgn`/`read-pgn`
over Typst's `read`, returning an array of games; and three rendering paths
(mainline spine, in-PGN RAV branches, and non-destructive `line(...)` overlays)
all funneling into the existing `position + style → renderer` seam.
