# Subtask 3.4 — Drawing improvements: design discussion

> Status: **implemented.** This was the design discussion; the recommendations
> below were then built into `src/board.typ`, `src/pieces.typ`, `src/style.typ`,
> `src/game.typ` and `lib.typ`, with coverage in `tests/api.typ`, the new
> `tests/fail/*` guard cases, and `examples/gallery.typ`. Subtasks 3.1–3.3 were
> already implemented.

## Decisions (resolved as implemented)

1. **SVG recoloring**: kept each set at its built-in colors; `white-fill` /
   `black-fill` apply only to the unicode fallback. (Recommended option.)
2. **on-square labels under flip**: implemented lichess-style — labels stay on
   the outer display edge (file letters along the file-side edge, rank digits on
   the rank-side edge) and move with the flip, reading `h…a` left-to-right when
   flipped. `file-side` / `rank-side` still pick the edge.
3. **Naming**: kebab-case `game-info:` (above) + `caption:` (below) + `flip:` +
   `label-mode:` + `set-piece-set()`.
4. **on-square label z-order**: coords drawn *over* everything in the corner
   (lichess-style); pieces have enough margin that corners stay clear.

---

## Where things stand today

The current architecture is well-positioned for 3.4:

- **One renderer, one positioning function.** `src/board.typ` `_screen(col, row,
  sq, orientation)` is the single place orientation/flip is resolved; squares,
  pieces, highlights and label strips are all `place`d through it. This is the
  seam every new feature reuses.
- **3-layer style merge.** `render-board` resolves `default-style ⊕ style-state
  ⊕ overrides` (`src/board.typ`, `src/style.typ`). Adding an option is mostly
  "add a key to `default-style`."
- **A (kind, color) → content seam.** `src/pieces.typ` `piece-content` already
  isolates glyph rendering and its own comment anticipates SVG sets (it says
  "subtask 3.5" — stale, it is 3.4 now).

Of the five sub-items, three are small (adjustable colors, flipping geometry,
set selection plumbing) and two are invasive (SVG piece sets, three label
modes). Below, each item lists *what changes* and *where it lands*.

---

## 1. Figure / diagram labeling — moderate; touches `lib.typ`

Today `lib.typ` collapses every source into a bare board via `_to-board`, then
emits a single `figure(caption: ...)`. `_default-caption` builds
"White – Black, Event Year" and renders it *below*. The new rules need **two**
label slots and **source-aware** defaults.

### Required behaviour (from the prompt)

- **Above**: if players + year are known, auto-draw `"<WHITE> - <BLACK> (<YEAR>)"`
  above the diagram; otherwise nothing above. (Prompt line 159 writes
  `<PLAYER_WHITE>` twice — read as white–black.)
- A manual `game-info` / `label_above` overrides the default above-line.
- **Below** (default caption), by source:
  - FEN source → `"Position at move <fullmove>, <color> to play"`.
  - PGN source → `"Position after move <last move in PGN>"`.
  - manual piece/position dict → **no** default label.
- A manual `caption` overrides the default below-line.

### Design

**a) Two slots, not one.** Typst `figure` has only one (numbered, below)
caption. Therefore:

- **Below** = the figure `caption` (keep using it) → becomes the *position* line.
- **Above** = "game info" → prepend into the figure **body** as a `stack` of
  `[game-info]` then the board. It is a title, not a numbered caption, so keeping
  it out of `figure.caption` is semantically correct.

So the figure body becomes `stack(game-info-line, render-board(...))`; the
caption stays on the figure.

**b) Preserve provenance.** `_to-board` currently discards both the source type
and the position metadata (`turn`, `fullmove`). To produce source-specific
defaults we must know where the diagram came from. A `parse-fen` position and a
manual `position()` dict are structurally identical, so we cannot discriminate
by inspecting the value — **discriminate by entry function**, which expresses
intent:

| Entry | Provenance | Above line | Below default |
|-------|-----------|------------|---------------|
| `fen-diagram` / `chess-diagram(<str>)` | FEN | from `white/black/year` if given | "Position at move N, X to play" (from `turn` + `fullmove`) |
| `board-after(game, locator)` | PGN | from `game.tags` (roster) | "Position after move \<last SAN\>" (from `game.movetext`) |
| `chess-diagram(<dict>)` | manual | from `white/black/year` if given | none |

`board-after` already holds the `game`, so it can pull the last move's SAN at
the locator and the `white/black/event/year` tags "for free."

Concretely: split `_default-caption` into `_game-info-line` (above) and
`_position-caption` (below, provenance-specific); each public entry computes its
own two lines and forwards to one shared internal
`_emit-figure(body, game-info, caption, ..fig-args)`. Manual `game-info=` /
`caption=` short-circuit the respective default.

**Naming**: standardize kebab-case `game-info:` (above) + `caption:` (below),
matching the existing `..args` splitter and Typst convention (open decision 3).

## 2. SVG piece sets — the biggest change; touches `pieces.typ` + `board.typ` + `style.typ`

`assets/piece_sets/<set>/{w,b}{K,Q,R,B,N,P}.svg`, six sets, lichess-style 45×45,
`cburnett` the factory default. The SVGs carry the correct baseline already.

> **Data fix required:** `assets/piece_sets/california/bB (1).svg` must be
> renamed to `bB.svg`, or the california black bishop will not resolve.

### Design

**a) The seam absorbs the mode.** Extend `piece-content` (or a sibling) to take
the **square size** and a **`set` name** and return content already sized to the
square:

- `set == "unicode"` / `none` → today's glyph path (keep per-kind
  `piece-size-ratio`, the `bounds` baseline trick, fill + stroke).
- otherwise → `image(<path>)` filling the square, with **no** baseline inset,
  **no** per-kind ratio, **no** bottom alignment.

This pulls the baseline math **out of `board.typ`.** Today board.typ owns it (the
`inset: (bottom: sq * baseline-inset)` + `align(center + bottom)` +
`sq * piece-scale` block). Per the prompt ("remove any baseline adjusting code;
exception: fallback"), board.typ should just `place` a square-sized piece and let
`pieces.typ` decide centering-vs-baseline by mode. This is the right ownership
and is required to drop the baseline code for SVGs.

**b) Path resolution.** `image()` resolves relative to the *calling* `.typ`
file, so a runtime-built path like
`"../assets/piece_sets/" + set + "/" + <wK> + ".svg"` from `pieces.typ` works and
survives packaging (a Universe package bundles assets at a fixed relative root).
Need a `kind → letter` map (king→K, knight→N, …) and `color → {w, b}`. The
`read()` + `image(bytes, format: "svg")` alternative is only worth it if we want
recoloring (see d).

**c) Selecting the set / fallback.** Make `piece-set` a normal `default-style`
key (default `"cburnett"`); per-diagram override and the 3-layer merge then come
for free. Add `set-piece-set(name)` as sugar over
`set-chess-defaults(piece-set: name)` so both requested forms work. **Do not
probe the filesystem** (Typst cannot test file existence without erroring):
maintain a known list of bundled sets, and reserve `"unicode"` / `none` as the
explicit sentinel selecting the glyph fallback.

**d) Coloring of SVG pieces — open decision 1.** The cburnett SVGs hard-code
their colors (white fill `#fff`, black outline). The "adjustable colors" item
really targets **square** colors (`light` / `dark`), which are independent of the
piece set and already adjustable (see §3). Recommendation: **`white-fill` /
`black-fill` apply only to the unicode fallback**; SVG sets keep their built-in
look in v1. Recoloring SVGs means per-set string substitution of fill colors (the
six sets differ in internal conventions) — fragile; defer it.

## 3. Adjustable colors — essentially already done

`light`, `dark`, `white-fill`, `black-fill`, `label-color`, `highlight-fill`,
`border` are already style keys resolved through `default ⊕ state ⊕ overrides`,
and `set-chess-defaults` already persists them document-wide until reset/changed
(`src/style.typ`). That satisfies "settable as default, used for subsequent
diagrams." The only new wrinkle is the SVG-piece-color semantics (§2d). No real
work here beyond confirming intent.

## 4. Board labeling — three modes; most layout-invasive part of `board.typ`

Today there is effectively one mode: external **gutter strips** — that is the
prompt's "mode 2 (same as before)." Add a `label-mode` style key:
`"on-square"` (default) | `"outside"` | `"border"`, with `labels: bool`
remaining the master on/off.

- **on-square (new default):** tiny file letters in the **bottom-left corner** of
  the rank-1 squares (a1–h1), rank digits in the **top-right corner** of the
  h-file squares (h1–h8); h1 carries both. Drawn *inside* the board canvas as
  corner `place` overlays → **no gutter**, the board fills the whole figure. Label
  fill = the **opposite square color** (`st.dark` on a light square, `st.light` on
  a dark square). Geometry reuses `_screen` for the square origin plus a small
  corner offset.
- **outside:** today's strips, unchanged.
- **border:** grow the figure box by N pt, fill that ring with `st.dark`, center
  labels in it using `st.light`.

### Consequences

- **Gutter is now mode-dependent.** `_resolve-size`'s `gutter-ratio` must be
  computed per mode: 0 for on-square, the strip ratio for outside, the border
  width for border.
- **Dedicated label font.** The prompt requires board labels to use a fixed
  sans-serif (Helvetica/Arial), independent of the main text and diagram font,
  not adjustable for now. Add a `board-label-font` constant
  (`("Helvetica", "Arial", "DejaVu Sans")`) and `set text(font: ...)` in the
  label code; today labels inherit the document font.
- **top/left still respected.** For *outside* mode it moves the strips (as
  today). For *on-square* (open decision 2): `file-side` / `rank-side` choose
  *which* edge rank/file carries the labels (file-side:top → letters on rank 8;
  rank-side:left → digits on the a-file), while the within-square corner anchoring
  stays fixed (file: bottom-left, rank: top-right). The prompt (lines 198–200) is
  slightly ambiguous here; this is the working interpretation.
- "No labels" (`labels: false`) is honored in all modes.

## 5. Board flipping — geometry done; only the *policy* needs fixing

`orientation: "white" | "black"` is already a style key and `_screen` already
flips squares, pieces, **and** label strips with it, so the flip itself works.
The only mismatch with the prompt: flipping **must not be a persistable
default**, but `orientation` currently lives in `default-style` and is therefore
settable via `set-chess-defaults`.

**Fix:** promote flipping to a dedicated per-call argument — `flip: false` on the
diagram / render entry points — and **remove it from `style-keys`** so
`_split-args` routes it as a render arg and `set-chess-defaults` cannot persist
it. Internally map `flip → orientation`. The on-square and border label code must
also go through `_screen` (the strips already do), so they flip automatically and
"labeling must be adjusted accordingly" is satisfied for free.

## Cross-cutting refactors this implies

1. **`render-board` stops owning piece baseline math** — delegate sizing /
   centering to `pieces.typ` (§2a). Required to drop baseline code for SVGs.
2. **`lib.typ` preserves provenance** (FEN vs PGN vs manual) instead of
   flattening through `_to-board`, to drive the two label slots (§1b).
3. **Style key changes:** add `label-mode`, `piece-set` to `default-style`; move
   `flip` / `orientation` *out* of `style-keys` (§§2c, 4, 5).
4. **Data fix:** rename `california/bB (1).svg` → `bB.svg`.
5. **Doc tidy:** correct the stale "subtask 3.5" comment in `src/pieces.typ`.

## Follow-up refinements (post-implementation)

After the first pass, four tweaks were made:

1. **Smaller, corner-hugging on-square labels.** The on-square label size dropped
   from `0.42` to `0.26` of a square and the corner inset from `0.06` to `0.02`,
   so the file/rank coordinates sit tucked into the bottom-left / top-right
   corners instead of dominating the square. (`_on-square-label-frac`,
   `_on-square-pad-frac` in `src/board.typ`.)
2. **Auto-fallback to "border" when tiny.** When an `"on-square"` diagram's
   corner labels would render at or below `_on-square-min-size` (4pt) — i.e. on
   small boards — that diagram switches to `"border"` labeling automatically, so
   coordinates stay legible. The decision is made inside `layout()` after the
   board size is resolved.
3. **A public `board(source, ..)` primitive.** Draws just the board (no figure /
   caption); `chess-diagram` / `fen-diagram` now wrap it. Same `source` forms,
   `flip`, and style overrides as `chess-diagram`.
4. **Scaling test.** `tests/scaling.typ` renders the same position across a range
   of sizes for every label mode (plus a flipped row), to eyeball how labeling
   and the auto-fallback hold up as the board shrinks.
